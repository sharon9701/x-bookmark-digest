# Skill 修改协议

当试跑、用户反馈或回归测试指出某类结果有问题时，必须按本协议修改。目标是修正产生问题的通用规则，不是让一个示例恰好通过。

## 1. 抽象问题，先停手再修复

先用一句话描述可复现的问题，再回答两个问题：

- 这个现象背后的共同机制是什么？例如是媒体渲染能力差异、队列状态错误、窗口判定错误，还是输出契约不清。
- 问题属于哪一层：触发与范围、数据与状态、注释规则、渲染与交互、宿主适配，还是安全门槛？

如果只能说“这个例子不对”，还没有找到可迁移的规则，禁止直接添加该例子的特判、关键词或固定输出。

## 2. 修复规则层，不修补单个案例

根据问题所在层修改真正控制行为的地方：

- 约束、决策顺序和禁止事项写入 `SKILL.md` 或对应 reference；
- 确定性行为写入脚本、配置默认值或 schema；
- 宿主差异写入适配边界和稳定回退；
- 示例只用于说明规则，不作为隐藏的额外规则。

修改必须覆盖同一机制的正向、反向和失败路径。不得通过删除校验、放宽所有输入或把错误静默掉来让单个案例通过。

## 3. 做影响面分析

在提交修改前列出受影响的全部场景，不得只看触发本次反馈的样例。至少检查：

- 不同输入来源、内容类型和数据完整度；
- single、batch、首次运行、续跑、空队列和失败恢复；
- 正常、边界、异常和宿主能力不足；
- 本地文件、数据库、外部连接器、聊天渲染和其他 Agent 适配层；
- 用户动作、副作用、幂等和权限边界。

同时写明哪些行为保持不变，避免为了局部修复而扩大无关改动。

## 4. 用覆盖型测试集回归

每次修改至少准备 3–5 个测试场景，一次覆盖不同方向：

- 一个熟悉的正常场景；
- 一个同机制但不同输入的变体；
- 一个边界或空值场景；
- 一个失败、降级或宿主不支持场景；
- 必要时再加一个与原案例相反的场景，验证规则没有过度放宽。

测试应验证用户可观察行为和状态结果，不要只断言某个示例字符串。原案例通过只是必要条件，不是充分条件。若修改涉及脚本，运行完整测试；若只涉及文档，也要检查引用路径、配置示例和可执行命令。

## 5. 记录与回退

在变更说明中记录：问题的通用机制、修改的规则层、影响面、覆盖的测试和仍保留的限制。若回归失败，回到第 1 步重新抽象，不继续叠加特判。若暂时无法找到通用规则，明确标记为未解决并保留可复现输入，不能假装已修复。

## 最小执行模板

```text
问题：可复现的用户可观察现象
共同机制：导致多个场景出现该现象的规则或边界
修改层：SKILL / reference / script / config / adapter
影响面：输入、模式、边界、宿主、副作用
回归集：正常、变体、边界、失败（至少 3–5 个）
结果：通过项、剩余限制、回退方案
```
